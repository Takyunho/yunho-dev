# 3D 장면 교체 설계: 코드가 UI 부품이 되는 장면

작성일: 2026-09-18

## 배경과 목표

v1.0.0의 3D 장면은 추상 도형 40개가 물리로 뭉치는 덩어리였다. 이것을 "프론트엔드 개발자"가 읽히는 장면으로 바꾼다. 컨셉은 프로토타입(저장소 밖 단일 HTML)으로 검증한 M안이다.

1. 히어로에서는 실제 코드 글자가 화면 아래에서 위로 기둥처럼 올라간다. 색은 몽환적인 청록과 보라다.
2. 스크롤을 내리면 글자 입자들이 날아가 UI 부품 여섯 개(브라우저 창, 테마 토글, 반응형 기기, 모달, 체크박스, 코드 괄호)의 표면에 내려앉고, 점이 채워지듯 광택 있는 입체로 굳어진다.
3. 굳은 부품은 About에서 한 덩어리로 머물다가 Stack부터 Lab까지 본문 양옆으로 흩어져 머문다. 여백이 좁은 화면에서는 문구 사이 빈 공간에 둘씩 들어간다.
4. Contact에서는 부품이 다시 뭉쳤다가 점과 코드 기호로 풀려 화면 아래에 고이고, 커서가 점에 닿으면 파도처럼 솟았다 가라앉는다. "Let's talk"와 이메일 글자도 파도를 따라 출렁인다.

라이트 모드와 다크 모드, 서버 렌더링되는 DOM 콘텐츠, 동작 줄이기와 WebGL 대체 처리는 v1.0.0의 원칙을 그대로 지킨다.

## 범위에서 제외하는 것

- 글자가 물결 모양으로 휘는 표현. 글자는 한 자 단위로 오르내리고 기울기만 한다. 휘게 하려면 텍스트를 WebGL로 그려야 해서 범위가 커진다.
- 후처리(`@react-three/postprocessing`), Next.js 16 업그레이드, GitHub API 연동. 이전 설계와 같다.
- 섹션 구성과 콘텐츠 변경. 마지막 섹션의 글자를 span으로 나누는 것 외에 DOM 문구는 바꾸지 않는다.
- 진짜 유체 시뮬레이션. 파도는 64칸 1차원 수면으로 흉내 낸다. 프로토타입에서 이 정도로도 참고 영상의 움직임 구조(커서 자리에서 솟아 양옆 두 물결로 갈라짐)가 나오는 것을 확인했다.

## 결정 사항

### 물리 엔진을 장면에서 쓰지 않고 위치 보간으로 바꾼다

장면에서 `@react-three/rapier`를 쓰지 않는다. 패키지는 사용자 결정에 따라 `package.json`에 그대로 남긴다(장면 코드에서 import하는 곳만 없어진다). 이유는 세 가지다.

- 이 컨셉에서 부품의 자리는 정확해야 한다. 옆 배치는 본문 여백 한가운데, 문구 사이 배치는 문구가 없는 빈 공간 안이어야 하는데, 물리는 부품끼리 밀치며 자리를 벗어난다.
- 부품이 굳어지는 동안 입자가 부품 표면을 따라가야 해서 매 프레임 부품의 행렬을 셰이더에 넘긴다. 위치를 코드가 정하면 이 동기화가 단순해진다.
- WASM 로딩과 초기화(형태별 충돌체를 써도 2~3초)가 없어져 첫 장면이 빨라진다.

커서에 밀리는 느낌은 물리 없이 남긴다. 커서가 부품 가까이 오면 부품이 커서 반대쪽으로 조금 기울고 밀렸다가 스프링처럼 돌아온다.

### 옆 배치와 문구 사이 배치를 여백 측정으로 고른다

미디어 쿼리 폭이 아니라 본문 바깥 여백의 실제 크기로 판단한다. 가장 넓은 부품을 하한 배율(0.6)로 줄이고 최소 간격을 더한 너비가 여백에 들어가지 않으면 문구 사이 배치다. 사용자가 보고한 1324×2000처럼 너비는 넓어도 세로가 길어 장면이 좁아지는 창까지 잡힌다.

본문 컨테이너가 프로토타입(1040px)보다 넓은 `max-w-6xl`(1152px)이라 여백이 그만큼 좁다. 이 규칙으로 1512×982와 1440×900은 옆 배치, 1366×768 이하와 1324×2000, 1024×768, 휴대폰은 문구 사이 배치가 된다. 1440×900이 옆 배치에 들도록 브라우저 창 부품의 반너비를 프로토타입의 1.8에서 1.5로 줄인다(계산은 "배치 방식 선택" 절).

### 렌더링 라이브러리는 유지한다

React Three Fiber 9와 drei 10 위에서 구현한다. 입자는 `THREE.Points`와 `ShaderMaterial`, 부품은 `group`과 `MeshPhysicalMaterial`이고, 조명 환경(`SceneLighting`)은 지금 것을 그대로 쓴다. 프로토타입은 순수 three.js였지만 셰이더와 계산 코드는 그대로 옮길 수 있다.

## 아키텍처

### 레이어 구조

이전 설계와 같다. 뒤에 고정된 투명 `Canvas` 하나, 앞에 Lenis로 스크롤되는 DOM 섹션이다. 여기에 안개 층 하나가 더해진다.

- `Atmosphere`: `Canvas`보다 뒤에 있는 `position: fixed` div다. 테마별 CSS 토큰으로 청록과 보라 radial-gradient를 그린다. 몽환적인 색은 셰이더가 아니라 이 층이 만든다. 부품이 굳어지면 옅어지고 풀리면 다시 짙어진다.

### DOM과 3D 사이의 상태 전달

`sceneState`를 확장한다. 매 프레임 바뀌는 값이므로 React state가 아닌 가변 객체라는 원칙은 같다.

```ts
export const sceneState = {
  sectionProgress: 0,
  pointer: { x: 0, y: 0 }, // NDC
  pointerActive: false,
  // 커서가 움직인 거리(NDC)를 쌓은 값. 파도의 세기다. 3D 쪽이 프레임마다 줄인다
  pointerEnergy: 0,
  accentOverride: null as string | null,
  // DOM 쪽이 잰 레이아웃. 3D 쪽이 이것으로 옆 배치와 문구 사이 배치를 고른다
  layout: {
    contentMarginPixels: 0, // 본문 컨테이너의 왼쪽 여백
    // 부품이 들어갈 문구 사이 빈 공간. 문서 기준 픽셀이다
    gaps: [] as { top: number; bottom: number; band: number }[],
    contactTopPixels: 0, // Contact 섹션의 문서 기준 위쪽 y. 휴대폰 덩어리 고정용
  },
};
```

쓰는 쪽과 읽는 쪽은 다음과 같다.

| 값                         | 쓰는 곳                                          | 읽는 곳                                    |
| :------------------------- | :----------------------------------------------- | :----------------------------------------- |
| `sectionProgress`          | `SceneStateSync` (스크롤)                        | `UiParts`, `GlyphParticles`                |
| `pointer`, `pointerActive` | `SceneStateSync` (pointermove)                   | `UiParts`, `GlyphParticles`, `waveSurface` |
| `pointerEnergy`            | `SceneStateSync`가 더하고 `waveSurface`가 줄인다 | `waveSurface`                              |
| `accentOverride`           | `ProjectCard`                                    | `usePartMaterials`                         |
| `layout`                   | `SceneStateSync` (리사이즈, 글꼴 로딩)           | `UiParts`                                  |

파도 높이는 반대 방향으로 흐른다. `waveSurface` 모듈이 가진 `Float32Array`를 3D 쪽이 매 프레임 갱신하고, Contact 섹션의 DOM 글자가 `gsap.ticker`에서 읽는다.

## 연출 타임라인

`sectionProgress`는 0이 hero 중앙, 1이 about 중앙, 5가 contact 중앙인 연속 값이다(`SceneStateSync`가 계산하는 방식 그대로). `sectionChoreography.ts`는 이 값을 아래 단계 값들로 바꾼다. 각 단계는 시작과 끝 사이를 smoothstep으로 0에서 1까지 올린다.

| 단계 값        | 데스크톱과 태블릿                       | 휴대폰(768px 미만)     | 뜻                                                                           |
| :------------- | :-------------------------------------- | :--------------------- | :--------------------------------------------------------------------------- |
| `morph`        | 0.2 → 0.8 (도착 비율)                   | 0.05 → 0.4             | 입자가 기둥에서 부품 표면으로 날아간다. 입자마다 출발이 늦춰진다             |
| `clumpShift`   | 0.2 → 0.85 (도착 비율)                  | 사용 안 함             | 덩어리가 About의 오른쪽 절반으로 이동한다                                    |
| `solid`        | 0.65 → 0.95 (도착 비율)                 | 0.3 → 0.5              | 부품이 `alphaHash`로 점이 채워지듯 굳는다. `dissolve`가 진행되면 그만큼 뺀다 |
| `particleFade` | 0.75 → 1 (도착 비율), 4.7 → 4.84 (돌아옴) | 0.4 → 0.6, 4.74 → 4.88 | 부품으로 모이지 않은 입자가 사라졌다가 마지막에 돌아온다                     |
| `spread`       | 1.1 → 1.6                               | 0.8 → 1.3              | 덩어리에서 각자의 자리(옆 또는 문구 사이)로 흩어진다                         |
| `regather`     | 4.15 → 4.5                              | 4.5 → 4.78             | 자리에서 Contact의 덩어리로 돌아온다                                         |
| `dissolve`     | 4.72 → 4.92                             | 4.76 → 4.94            | 굳은 표면이 점 단위로 빠져 점묘로 돌아간다                                   |
| `pool`         | 4.74 → 4.99                             | 4.78 → 4.99            | 점이 중력처럼 떨어져 바닥에 고인다. 파도는 `pool > 0`일 때만 계산한다        |

"도착 비율"로 적은 구간은 `sectionProgress`를 About에 도착하는 진행도(`sceneState.aboutArrivalProgress`, About 섹션의 위쪽이 화면 위쪽에 맞춰졌을 때의 값)로 나눈 값에 적용한다. 헤더의 About을 눌러 도착한 위치에서 부품이 다 굳어 있게 하려는 것이다. About이 화면보다 길수록 이 값은 1보다 작아지고, 0.6보다 작아지지는 않게 한다. 휴대폰의 구간은 절대값 그대로다.

마지막 네 단계의 데스크톱 값은 옆 배치(본문 양옆에 여백이 있는 화면) 기준이다. 여백이 없어 문구 사이에 배치하는 태블릿은 마지막 네 단계에 휴대폰 열의 값을 쓴다. `sectionChoreography.ts`는 이 셋을 `SceneProfile`(`side`, `stacked`, `mobile`)로 구분하고, `resolveSceneProfile`이 휴대폰 여부와 측정한 여백으로 정한다.

`spread`는 `regather`가 진행되면 그만큼 뺀다. 마지막 구간의 어려움은 Lab이 내용 높이만큼만 차지하는 섹션이라 Lab 중앙에서 Contact 중앙으로 가는 동안(4.0부터 4.9 가까이까지) Lab 목록이 화면 위쪽에 남고, 그 아래로 Contact의 제목 "Let's talk"과 링크가 화면 왼쪽 가장자리(본문 여백 안)를 지나 올라온다는 점이다. 곧장 뭉치면 위쪽 부품이 목록을, 왼쪽 부품이 제목을 가로지르고, 왼쪽 여백에 그대로 두어도 4.4 무렵 올라오는 제목과 이메일이 토글을 덮는다.

옆 배치는 그래서 4.15부터 4.5까지 빈 줄 경로(`computeLaneRoute`)로 다시 뭉친다. Lab 목록 아래 여백과 Contact 위 여백이 같아서 섹션 경계(`contactTopPixels`)가 둘 사이 빈 줄의 가운데다. 부품은 먼저 자기 자리에서 이 빈 줄로 내려오고(`descend`, regather 0 → 0.35), 빈 줄을 따라 덩어리 자리의 x까지 건너간 뒤(`traverse`, 0.3 → 0.8), 덩어리 자리로 들어간다(`settle`, 0.65 → 1). 빈 줄이 섹션 여백 두 개 높이라서 건너가는 동안 부품을 최대 30% 줄인다(`sin(traverse × π)`). 덩어리는 섹션에 문서 기준으로 고정되어 4.5부터 4.72까지 섹션과 함께 올라오다가, 4.72부터 4.99에 걸쳐 천천히 풀려 웅덩이에 고인다. 왼쪽 부품이 오른쪽으로 건너간 뒤에 파도로 변하는 순서가 보이도록 한 것이다.

문구 사이 배치(태블릿)와 휴대폰은 다시 뭉칠 때 부품의 자리가 Lab 목록 위쪽, 화면 밖이다. 거기서 내려오면 목록과 Contact 제목을 가로지르므로, 부품은 화면 아래 밖에서 덩어리 자리(섹션 위에서 화면 높이의 0.6배, 링크 아래)로 곧장 올라온다. 덩어리 자리 아래에는 문구가 없어서 어디와도 겹치지 않는다. 이때 덩어리 중심은 히어로나 About 자리와 섞지 않고 처음부터 Contact 자리로 둔다. 4.5부터 4.78까지 천천히 올라와 다 모인 뒤 4.76부터 4.94까지 풀리고 4.78부터 4.99까지 고인다. 내려오자마자 점으로 변하던 첫 값(4.7 → 4.88에 모이고 4.86부터 풀림)을 사용자 피드백으로 늘린 것이다. 세로로 긴 창에서는 덩어리의 x를 오른쪽 부품이 화면 밖으로 나가지 않는 자리로 당긴다.

휴대폰은 About 문구가 화면 너비와 높이를 거의 다 써서 화면에 고정된 덩어리를 둘 자리가 없다. 그래서 덩어리를 히어로에 문서 기준으로 고정한다. 스크롤이 화면 높이의 22%를 넘기 전까지는 화면 위쪽(반높이의 0.35배 위)에 머물러 굳는 모습이 보이고(그래서 휴대폰은 모이고 굳는 구간을 앞당긴다), 그 뒤로는 히어로와 함께 밀려 올라가 About 문구와 겹치지 않는다. 흩어지고 다시 뭉칠 때의 이동 경로는 문구를 가로지르지 않도록 화면 옆 가장자리(부품별 옆 배치 방향으로 반너비의 1.3배, `sin(spread × π)`)로 돌아 나갔다가 자리로 들어온다. v1.0.0에서 모바일 About 문구와 덩어리가 겹치던 문제가 이것으로 없어진다. Contact에서도 같은 이유로 덩어리를 섹션에 문서 기준으로 고정해, 섹션이 들어오는 동안 제목이 덩어리를 지나가지 않는다.

덩어리의 중심과 크기는 다음과 같다.

- 데스크톱과 태블릿: 히어로에서 화면 중앙 조금 위, `clumpShift`에 따라 About 문구의 오른쪽에 남는 영역의 가운데로 이동. 영역은 측정한 문구 오른쪽 끝(`aboutTextRightPixels`)부터 화면 끝까지에서 양쪽 간격 0.5단위를 뺀 너비다. 세로로 긴 창처럼 이 영역이 덩어리 너비(부품 정의에서 구한 좌우 끝의 합, 약 7.3단위)보다 좁으면 덩어리를 영역에 맞춰 0.35배까지 줄이고, 줄인 배율은 흩어지기 시작하면 원래대로 돌아간다. 화면 반너비의 비율(0.44배)로 자리를 정하던 첫 구현은 1465×2000 같은 창에서 덩어리가 문구를 덮었다. Contact에서는 휴대폰과 같이 섹션과 함께 올라오는 자리에 문서 기준으로 고정한다. 옆 배치는 Lab이 아직 화면에 있을 때 뭉치므로 그때 화면에 들어와 있는 높은 자리(섹션 위에서 화면 높이의 0.32배, x는 반너비의 0.6배)에 두어 정렬되면 "Let's talk"의 오른쪽이자 링크 옆이고, 문구 사이 배치는 제목과 링크가 지나간 뒤에 뭉치므로 그 아래(0.6배, x는 반너비의 0.5배)에 둔다. x가 다른 이유는 옆 배치에서는 제목의 오른쪽 끝을 넘겨야 하고, 좁은 태블릿에서는 오른쪽 부품이 화면 밖으로 나가면 안 되기 때문이다.
- 휴대폰: 히어로에서 화면 중앙 위쪽(반높이의 0.35배 위, 문서 기준 고정), Contact에서는 섹션과 함께 올라오는 자리(섹션 위에서 화면 높이의 0.6배, 정렬되면 제목과 링크 아래이자 웅덩이 위)에 문서 기준으로 고정.
- 크기 배율은 `min(1, 화면 반너비 / 5)`다. 좁은 화면에서 덩어리가 화면을 넘지 않게 한다.

카메라는 z 18, fov 35로 고정한다. v1.0.0의 섹션별 카메라 거리 키프레임은 없앤다. 부품 자리를 화면 픽셀에 맞춰 계산하므로 카메라가 움직이면 계산이 복잡해진다.

## 입자 (GlyphParticles)

### 구성

- `THREE.Points` 하나. 입자 수는 데스크톱 112열 × 104개 = 11,648, 휴대폰 48열 × 84개 = 4,032이다.
- 글자판은 실행 시 canvas에 그린다. 10×10 격자에 ASCII 32부터 126까지를 고정폭 글꼴로 그려 텍스처로 만든다. 외부 이미지 파일을 두지 않는다.
- 입자마다 코드 코퍼스의 글자를 하나씩 배정한다. 코퍼스는 이 사이트 자체의 코드 조각(JSX, CSS, TypeScript 문장 십수 줄)으로 `glyphAtlas.ts`에 문자열 배열로 둔다. 열마다 코퍼스의 다른 위치에서 시작해 위에서 아래로 읽으면 실제 코드가 읽힌다.

속성은 다음과 같다.

| 속성        | 내용                                                                 |
| :---------- | :------------------------------------------------------------------- |
| `aStream`   | 기둥에서의 x, 시작 위상 y(0~1), 깊이 z                               |
| `aRandom`   | 열 속도, 입자 시드, 부품 번호, 열 시드                               |
| `aTarget`   | 배정된 부품 표면의 점(부품 로컬 좌표). `MeshSurfaceSampler`로 뽑는다 |
| `aGlyph`    | 글자판 인덱스                                                        |
| `aPool`     | 웅덩이에서의 가로 위치 u(-1~1), 높이 비율(0~1), 깊이                 |
| `aPoolMeta` | 웅덩이 참여 여부, 난수(기호 선택과 밝기)                             |

### 정점 셰이더 단계

1. 기둥: `fract(위상 + 시간 × 열 속도)`로 아래에서 위로 올라가고 끝에 닿으면 아래에서 다시 시작한다. 깊이가 멀수록 흐리고 어둡다. 1.5% 정도만 밝고 나머지는 어둡다. 기둥을 따라 올라가는 밝은 띠를 하나 얹는다.
2. 모임: `uMorph`에서 입자별 지연을 뺀 값으로 기둥 위치와 부품 표면 위치(`uPartMatrices[부품 번호] × aTarget`)를 보간한다. 날아가는 동안 호를 그리고, 내려앉은 뒤에는 아주 조금 떨린다. 크기는 글자 크기에서 점 크기로 줄어든다.
3. 웅덩이: `uPool`에서 입자별 지연을 뺀 값으로 현재 위치와 웅덩이 위치를 보간한다. y는 제곱으로 보간해 중력처럼 점점 빨라진다. 웅덩이 위치는 `바닥 y + 높이 비율 × 그 칸의 수면 높이`이고, 수면이 높은 쪽으로 입자가 쏠려 마루가 성기지 않게 한다. 마루 근처의 입자는 수면이 솟는 속도만큼 물방울처럼 튄다. 참여하지 않는 입자는 사라진다.
4. 커서 밀림: 뷰 공간에서 커서 근처의 글자를 커서 반대쪽으로 민다. 굳은 뒤에는 밀지 않는다.

입자의 60%만 부품으로 모이고 40%는 제자리에서 사라진다. 전부 날아가면 전환 도중이 지저분해진다. 사라진 입자는 마지막 구간에서 돌아와 웅덩이에 참여한다.

### 조각 셰이더와 혼합

- 점 하나의 가운데에 글자를 그리고 바깥 여백을 빛 번짐에 쓴다. `vMorph`가 1이면 글자 대신 둥근 점이다.
- 다크 모드는 `AdditiveBlending`이고 색은 어두운 청록(`#2b93b0`), 밝은 청록(`#aef3ff`), 점(`#57c8f2`)이다.
- 라이트 모드는 가산 혼합이 밝은 배경에서 보이지 않아서 `NormalBlending`으로 잉크처럼 그린다. 색은 `#3c4f9c`, `#0b1450`, `#1a2ffb`다. 프로토타입에서 이 버전이 잘 성립하는 것을 확인했다.
- 테마가 바뀌면 색은 보간하고 혼합 모드는 즉시 바꾼다. 배경색 전환(0.6초)과 겹치는 짧은 순간의 어색함은 감수한다.

## UI 부품 (UiParts)

### 형태

여섯 개를 코드로 만든다. 외부 모델 파일을 두지 않는다.

| 부품        | 구성                                       | 반너비 | 문구 사이 자리             |
| :---------- | :----------------------------------------- | :----- | :------------------------- |
| 브라우저 창 | 둥근 박스 본체, 상단 바, 점 3개, 안쪽 패널 | 1.5    | About과 Stack 사이, 왼쪽   |
| 테마 토글   | 알약형 트레이, 하늘 판, 초승달, 구름, 별, 원통 손잡이 | 1.5    | About과 Stack 사이, 오른쪽 |
| 반응형 기기 | 모니터(받침 포함), 태블릿, 휴대폰과 각 화면의 레이아웃 | 1.5    | Stack과 Work 사이, 오른쪽  |
| 모달        | 내용이 비치는 페이지, 가운데 떠 있는 창(제목 바와 X, 본문, 버튼 2개) | 1.25   | Stack과 Work 사이, 왼쪽    |
| 체크박스    | 둥근 박스, 체크 표시 캡슐 2개              | 0.6    | Work와 Lab 사이, 오른쪽    |
| 코드 괄호   | 캡슐 6개로 `< / >`                         | 1.2    | Work와 Lab 사이, 왼쪽      |

테마 토글, 반응형 기기, 모달은 처음 구현의 슬라이더, 버튼, 토글을 사용자 요청으로 바꾼 것이다. 버튼 자리는 한 번 검색창으로 바꿨다가, 입체로는 무엇인지 읽히지 않는다는 피드백으로 반응형 기기 묶음으로 다시 바꿨다. 모달도 한 번 고쳤다. 첫 모양은 빈 검은 판 위에 창이 오른쪽 아래로 삐져나오고 X와 버튼이 창 모서리에 걸쳐 있어 모달로 읽히지 않았다. 지금은 뒤 판에 상단 바와 카드가 비쳐 페이지로 읽히고, 창은 페이지 한가운데에 떠 있으며, 강조색 제목 바 안에 제목과 X가, 창 안쪽 오른쪽 아래에 취소와 확인 버튼이 있다. 세 기기의 화면에는 같은 레이아웃(상단 바, 그림 블록, 글줄, 버튼)이 들어가는데, 모니터는 그림과 글줄이 나란히, 태블릿과 휴대폰은 위아래로 쌓여서 반응형이 읽힌다. 프론트엔드에서 더 대표적인 UI 요소로 읽히게 하려는 것이고, 자리와 덩어리 안 위치는 바꾸기 전 부품의 값을 물려받았다. 재질 역할에는 포인트 색(라임) `highlight`를 더해 해와 달, 모달의 확인 버튼, 기기 화면 속 버튼에만 쓴다. 테마 토글은 사용자가 보여 준 참고 이미지의 구성(알약형 트레이 안의 하늘, 왼쪽의 초승달, 가운데의 구름과 별, 오른쪽의 원통 손잡이)을 따른다. 트레이와 하늘 판은 알약 윤곽을 밀어 올려 만들고(`RoundedBoxGeometry`는 반지름이 두께의 절반으로 제한되어 알약이 되지 않는다), 초승달은 큰 원에서 작은 원을 뺀 윤곽을 밀어 올린다. 구름과 손잡이는 두 테마 모두에서 밝아야 해서 테마에 따라 뒤집히지 않는 재질 역할 `bright`를 쓴다. 다크 모드에서는 초승달과 별이, 라이트 모드에서는 해(눌린 구와 광선 8개)가 보인다. 이런 메시에는 `userData.themeOnly` 표식을 붙이고 `UiParts`가 테마에 맞춰 `visible`을 바꾼다. 입자는 표식이 붙은 메시를 표본에서 빼므로 보이지 않는 표면에 내려앉지 않는다. 테마 토글의 옆 배치 세로 비율(0.42)은 맞은편 브라우저 창과 같은 값이라 둘이 같은 높이에 놓인다. 체크박스(-0.04)도 같은 이유로 맞은편 코드 괄호와 같은 값을 쓴다. 입자가 부품 표면을 표본으로 삼으므로 모든 메시는 중첩 그룹 없이 부품 그룹의 직속 자식이어야 한다.

가장 작은 두 부품을 Work와 Lab 사이에 둔 이유는 그 빈 공간이 두 섹션의 padding만큼(데스크톱 256px, 휴대폰 192px)이라 가장 좁기 때문이다.

`partDefinitions.ts`의 각 항목은 생성 함수, 반너비, 덩어리 안에서의 상대 위치, 기본 회전, 옆 배치의 방향(왼쪽 -1, 오른쪽 1)과 세로 비율과 깊이, 문구 사이 배치의 빈 공간 번호와 좌우를 가진다. 부품의 높이는 생성 직후 기본 회전 상태의 `Box3`로 재서 문구 사이 배치에 쓴다.

### 재질

`usePartMaterials`는 지금의 `useClusterMaterials`와 같다. 중립, 대비, accent 세 재질을 모든 부품이 공유하고 테마 전환 시 색을 보간한다. 여기에 두 가지가 더해진다.

- `alphaHash`를 켜고(`transparent`는 켜지 않는다. alphaHash는 불투명 패스에서 깊이를 쓰며 동작한다) `opacity`를 `solid` 값으로 둔다. 점이 채워지듯 굳고, 풀릴 때는 그 반대다. 프로토타입에서 확인한 표현이다.
- 굳어지는 순간에만 `emissiveIntensity`가 `sin(solid × π) × 0.55`로 올랐다 내려가 빛이 돈다.

### 매 프레임 자리 계산

`UiParts`는 `useFrame`에서 부품마다 다음을 한다.

1. `sectionChoreography`에서 단계 값을 읽는다.
2. 덩어리 자리 = 덩어리 중심 + 상대 위치 × 크기 배율.
3. 흩어진 자리 = `sceneLayout`이 옆 배치나 문구 사이 배치 규칙으로 계산한 자리(아래 절).
4. 위치 = 덩어리 자리와 흩어진 자리를 `spread`로 보간. 회전 = 기본 회전 + 시간에 따른 느린 흔들림 + `spread × 0.6`(y축).
5. 커서 반응 오프셋을 더한다.
6. `updateMatrixWorld` 후 `matrixWorld`를 `GlyphParticles`의 `uPartMatrices[i]`에 복사한다.
7. `visible = solid > 0.001`.

부품 `group`은 `UiParts`가 소유하고, `GlyphParticles`는 uniform 배열의 참조만 받는다. 두 컴포넌트는 `Scene`에서 같은 `Matrix4[]` 인스턴스를 공유한다.

### 커서 반응

커서 NDC를 z = 0 평면의 장면 좌표로 바꾼 점과 부품 위치의 거리가 부품 반너비(배율 적용)의 1.5배 안이면, 커서 반대 방향으로 최대 0.5단위 밀리고 12도까지 기운다. 목표 오프셋을 `THREE.MathUtils.damp`로 따라가고 커서가 멀어지면 0으로 돌아온다. 굳지 않은 상태(`solid < 1`)와 웅덩이 구간에서는 반응하지 않는다.

## 부품 배치 규칙 (sceneLayout)

`sceneLayout.ts`는 상태가 없는 순수 함수 모음이다. 입력은 뷰포트 크기, 카메라 상수, `sceneState.layout`, 부품 정의이고 출력은 부품별 자리와 배율이다.

### 장면 단위와 픽셀

카메라가 고정이라 z = 0 평면에서 장면 단위 1이 몇 픽셀인지는 `화면 높이 / (2 × tan(fov / 2) × 카메라 거리)`로 정해진다. 화면 반높이는 `tan(fov / 2) × 18 ≈ 5.67`단위이고 반너비는 여기에 화면 비율을 곱한 값이다. DOM 쪽은 픽셀만 재고 변환은 3D 쪽이 한다.

### 배치 방식 선택

`contentMarginPixels`를 장면 단위로 바꾼 여백이 `가장 넓은 부품의 너비 × 크기 배율 × 0.6 + 0.42`(하한 배율로 줄인 부품과 화면 끝 최소 간격) 이상이면 옆 배치, 아니면 문구 사이 배치다. 리사이즈마다 다시 판단한다.

예를 들어 1440×900은 여백이 184px(컨테이너 바깥 144px에 padding 40px)이고 장면 단위 1이 79.4px이라 2.32단위다. 가장 넓은 브라우저 창(너비 3.0)은 `3.0 × 1 × 0.6 + 0.42 = 2.22`이므로 옆 배치이고, 부품 안쪽 끝이 본문에 닿지 않는다. 1366×768은 여백 147px이 2.17단위라 문구 사이 배치다.

### 옆 배치

v1.0.0의 `spreadX: 1.0`(부품 중심이 화면 끝이라 절반만 보임)을 버리고 프로토타입의 규칙을 쓴다. 사용자가 부품이 화면 끝에 잘리지 않고 온전히 보이면서 끝에서 살짝 떨어지기를 원했기 때문이다.

- `fitScale = clamp(여백 / (부품 너비 + 0.7), 0.6, 1)`. 여백이 좁으면 부품을 줄이되 0.6배까지만.
- `edgeInset = clamp(여백 / 2, 부품 반너비 + 0.42, 부품 반너비 + 1.75)`. 기본은 여백 한가운데이고, 화면 끝에 닿지 않는 최소 거리와 아주 넓은 화면에서 본문 쪽으로 너무 들어오지 않는 최대 거리를 지킨다.
- `x = 방향 × (화면 반너비 − edgeInset) × depthRatio`, `y = 세로 비율 × 화면 반높이 × 1.3 × depthRatio`, `z = 깊이 × 3`. `depthRatio = (카메라 거리 − z) / 카메라 거리`로, 카메라에 가까운 부품이 원근 때문에 바깥으로 밀려 보이는 만큼 안쪽으로 당긴다.

### 문구 사이 배치

부품 여섯 개를 세 빈 공간에 둘씩 둔다. 자리는 문서 기준이고 CSS `position: sticky`처럼 움직인다.

- `SceneStateSync`가 섹션 문구 블록(`data-scene-text`)의 경계를 재서 빈 공간마다 문서 기준 `top`(위 문구의 아래)과 `bottom`(아래 문구의 위)을 기록한다. 리사이즈, `document.fonts.ready`, `ResizeObserver`(body)에서 다시 잰다.
- `band`는 위 섹션이 정렬됐을 때 문구 아래에 남는 여백과 아래 섹션이 정렬됐을 때 문구 위에 남는 여백 중 좁은 쪽에서 간격(화면 높이의 5%) 두 배를 뺀 값이다. 섹션이 화면에 정렬된 상태에서 부품이 잘리지 않고 들어갈 수 있는 높이다.
- `fitScale = clamp(min(화면 반너비 × 0.8 / 부품 너비, band / 부품 높이), 0.5, 1)`.
- 문서 y = `clamp(scrollY + 화면 높이 × 0.3, top + 간격 + 부품 반높이, bottom − 간격 − 부품 반높이)`. 빈 공간 안에서는 화면 위 30% 높이에 머물고, 빈 공간 끝에 닿으면 문구에 밀려 함께 스크롤된다. 빈 공간이 부품보다 작으면 가운데에 둔다.
- x = `좌우 × 화면 반너비 × 0.45`, z = 0.

이 규칙으로 어떤 섹션이 정렬되면 문구 위에 둘, 아래에 둘이 보이고, 스크롤 중에 문구가 부품 위를 지나가는 일이 없다. 프로토타입에서 1324×2000, 1024×768, 휴대폰 크기로 확인했다.

Work와 Lab은 내용 높이만큼만 차지하는 섹션이라 그 사이 빈 공간이 padding만큼이다. 가장 작은 부품 둘을 배정하고 `fitScale`로 줄인다. 그래도 답답하면 문구 사이 배치일 때 두 섹션의 아래위 padding을 키우는 것을 후속으로 검토한다.

## 웅덩이와 파도 (waveSurface)

### 웅덩이

- 웅덩이 참여 입자는 데스크톱 5,200개, 휴대폰 1,800개다. 가로세로 비율 6.5의 육각 격자에 흔들림을 더해 배치한다.
- 60%는 점이고 40%는 기호 `+ < > / { } ; =` 중 하나다.
- 바닥은 화면 아래 끝보다 0.15단위 아래, 평소 수면 높이는 화면 높이의 24%, 너비는 화면 반너비의 1.04배다.

### 시뮬레이션

CPU에서 64칸 1차원 수면을 계산해 높이와 속도를 uniform 배열로 넘긴다. 셰이더는 칸 사이를 선형 보간한다.

- 힘: 평소 높이로 돌아가려는 복원력(6), 옆 칸으로 번지는 장력(60), 감쇠(초당 e^-1.0). 평소 높이에는 잔잔한 사인 일렁임을 더한다.
- 커서 접촉: 커서 x 자리의 수면보다 커서가 아래(0.5단위 여유)에 있을 때만 힘이 생긴다. 잠긴 깊이가 1.5단위까지는 비례하고 그보다 깊으면 같다. 힘은 커서 자리에서 위로 향하고(70) 가로로 가우시안(범위 2.8)으로 퍼진다. 커서가 허공에 있으면 아무 일도 없다.
- 세기: `pointerEnergy`는 pointermove마다 이동 NDC 거리 × 6만큼 쌓이고(최대 1.5) 프레임마다 e^-2.5t로 줄어든다. 힘에는 `min(energy, 1)`을 곱한다. "최근 n ms 안에 움직였을 때만" 같은 시간 조건은 이벤트 간격이 불규칙하면 동작하지 않아서 쓰지 않는다.
- 상한: 화면 높이의 85%에 가까워지면(그 35% 아래부터) 힘이 0으로 줄어든다. 계속 흔들어도 수면이 화면 꼭대기에 벽처럼 붙지 않는다. 높이는 `[평소 × 0.3, 화면 높이]`로 잘라 둔다.
- 하위 스텝 2개, 프레임 시간 상한 1/30초.

프로토타입 측정(1024×768): 커서가 허공이면 반응 없음, 한 번 스치면 평소 2.72단위에서 최고 8.1단위(화면 높이의 70%), 계속 흔들면 10.7단위에서 멈춤.

### 터치 기기

터치 스크롤 중에는 pointermove가 오지 않고 pointercancel이 온다. 그래서 터치에서는 pointerdown(탭)이 그 자리에 에너지 1을 넣어 파도를 일으킨다.

Contact의 푸터(저작권, "Built with")는 웅덩이 위에 놓인다. 읽히도록 배경색 60% 반투명 띠를 깐다. 문구는 "Built with Next.js, React Three Fiber"로 바꾼다.

## 안개 층과 히어로 가독성

- `Atmosphere`는 `--atmosphere-a`(청록)와 `--atmosphere-b`(보라) 토큰으로 두 radial-gradient를 그린다. 다크는 `rgba(30,138,150,.5)`와 `rgba(88,66,176,.44)`에 가장자리를 어둡게 하는 비네트를 더하고, 라이트는 `rgba(26,47,251,.1)`와 `rgba(0,150,170,.1)`이다.
- 불투명도는 `1 − solid × 0.7`이다. `UiParts`가 `document.documentElement`의 CSS 변수 `--atmosphere-opacity`에 쓴다. 3D 쪽이 DOM에 쓰는 유일한 값이며, 매 프레임 같은 값이면 쓰지 않는다.
- 히어로 문구 블록 뒤에 배경색의 radial-gradient(`--title-shade`)를 깔아 지나가는 글자 기둥을 눌러 제목이 읽히게 한다.

## 부드러운 스크롤

`SmoothScroll.tsx`의 Lenis 옵션에 `lerp: 0.05`, `wheelMultiplier: 0.7`을 준다. 프로토타입에서 휠 300px 입력이 210px 이동에 약 1.3초 동안 미끄러지는 것을 측정했고 사용자가 이 느낌을 승인했다. `anchors: true`와 GSAP ticker 연동은 그대로다.

## 동작 줄이기, 모바일, 대체 처리

- `prefers-reduced-motion`: Lenis를 끄는 것은 지금과 같고, `SceneLoader`가 장면을 히어로 높이의 `absolute` 영역에 두어 함께 흘려보내는 것도 같다. 장면은 단계 값을 `solid = 1`, 나머지 0으로 고정해 굳은 덩어리가 히어로 위쪽 중앙에 정지해 있고, 입자와 파도와 글자 출렁임은 켜지 않는다. `frameloop`은 `demand`이고 테마와 리사이즈 때만 다시 그린다.
- 휴대폰: 입자 수와 웅덩이 참여 수를 줄이고, `dpr`을 1.5로 제한하며, 그림자를 끈다(지금과 같다).
- WebGL 미지원: `SceneLoader`의 CSS 그라데이션 대체를 유지한다. 안개 층은 WebGL과 무관하게 보인다.
- 창이 가려져 rAF가 멈추면 복귀 시 `delta`가 커진다. 프레임 시간 상한(0.1초)과 파도 하위 스텝 상한으로 튀지 않게 한다.

## 성능 예산

- 데스크톱 입자 11,648개는 정점 셰이더 하나로 그리므로 드로 콜 1개다. 부품은 group 6개(메시 약 30개)다.

- 목표는 데스크톱 60fps, 휴대폰에서 눈에 띄는 끊김 없음이다.
